# Spec-Driven Dev Skill Ver1.0 → Ver1.1 改訂レポート

作成日: 2026-08-24

## 経緯

`V1.0_testbed` の実地検証で、V1.0が対象とした5件+新設した3つの一般ルールはいずれも意図どおり機能した。その後、人間が **`docs/P004-traceability-matrix.md` と `docs/P302-deliver.md` の仕様ID・要求IDの対応**を確認する過程で、対応表の運用に不備が見つかった。

V1.1は、人間の判断により次を対象とする。**フェーズ構成・進め方は変更しない**(作業プロセス自体はV1.0で解消済みという認識)。上流文書へのID体系の導入(P001にREQ-IDを振る等)は、コストに見合わないため**行わない**。

1. P004の要求IDとP302の仕様IDを対応させる
2. 要求の一部しかテストで確認できていない場合、副IDで未カバー分を分離してから `OK` を付ける
3. 未充足がある場合、**出荷への影響**を判断して評価する
4. 識別子の表記ゆれをP010で検出できるようにする(追加調査により判明)
5. リポジトリ直下 `README.md` に紹介パートとMermaid図を追記する

## 1. P004の要求IDとP302の仕様IDの対応(`SKILL-P302-deliver.md`)

* **事象**: V1.0のL137は「仕様IDが既存文書にない場合は一時IDを付ける。`docs/P004-traceability-matrix.md` で既に要求IDが振られている場合はそれを使う」という**条件付きの弱い指示**であり、(a) 各仕様IDがどの要求IDに由来するかを表に残す義務、(b) P004の要求IDをすべて網羅しているかの確認義務、(c) 副IDの命名規約、のいずれも規定していなかった。
  * `V1.0_testbed` では結果的に `REQ-*` 30件がP004・P302で完全一致していたが、これは規定に支えられた結果ではない。
* **V1.1での変更**:
  * 対応表に **`要求ID` 列を追加**した。仕様IDが要求IDと同じ場合は両列に同じ値を書いてよい。対応する要求が無い行(業務フロー横断シナリオ等)は `-` とし、理由を「仕様内容」欄に添える。
  * **網羅性の確認を義務化**した。P004に載っている要求IDのうち本表に1行も現れないものが無いことを確認し、あれば `UNKNOWN` として行を起こす。
  * **副IDの命名規約 `{親ID}-{修飾子}` を明記**した。番号を振り直さず親の番号を引き継ぐ。副IDの `要求ID` 列には親と同じ要求IDを書く。
  * **識別子は設計書からそのまま転記する**ことを明記した(下記4と対になる規定)。
  * 表の基本形の例を、`要求ID` 列・副ID・`出荷影響` 列を含む形に差し替えた。
* **根拠**: 副IDの命名規約は、`V1.0_testbed` の実行担当が**規定が無いまま自然に発明していた**もの(`REQ-NFR-006-集約`、`SPEC-SCREEN-003-参加者選択`、`SPEC-NFR-002-運用`)を、そのまま規定として固定した。現場で有効に機能していた形を採用しており、新方式の発明ではない。

## 2. 未カバー分は副IDで分離してから `OK` を付ける(`SKILL-P302-deliver.md`)

* **事象**: `V1.0_testbed` の `REQ-NFR-003` で、P004が「セキュリティ(HTTPS/パスワードハッシュ/権限チェック)」と3観点を挙げているのに対し、P302はこれを「セキュリティ(パスワード非露出)」と読み替え、A008(パスワード非露出テスト)1件をもって `OK` と判定していた。
  * 実態は、**権限チェック**はA003でカバー済みだがREQ-NFR-003の行からは辿れず、**HTTPS**は未カバーだった。
  * その結果、**同一文書内で、11章は「TLS未終端」を保留理由に繰り返し挙げながら、4章の対応表は同じ要求を `OK` と判定する**という食い違いが生じていた。対応表だけを読んだ人は「セキュリティ要件は検証済み」と受け取る。
  * **同じP302が `REQ-NFR-006` では正しく処理していた**(ログ集約基盤への転送を `REQ-NFR-006-集約` として別行に切り出し `BLOCKED` + 理由付きで開示)。適切な扱い方は分かっていたが、規定が無いため適用が一貫しなかった。
* **V1.1での変更**: 「対応表作成時のルール」に次を追加した。
  * **`OK` を付けてよいのは、引用したテストが要求内容の全体をカバーしている場合に限る。**
  * 一部しかカバーできていない場合の手順を3ステップで規定した。(1) 親行の「仕様内容」を**範囲を狭めたと分かる書き方**にする、(2) 未カバー分を副IDで別行に起こし状態と理由を書く、(3) 複数テストにまたがる場合は証跡を**すべて**挙げる。
  * 禁止事項に「要求の一部しか確認していないのに `OK` と書かない」「仕様内容欄を書き換えて要求の範囲を黙って狭めない」を追加した。
  * 11章に「**4章の対応表と本章の判定が食い違ってはならない**。食い違う場合は副IDによる切り出しが済んでいないことを意味するので、判定を書く前に4章へ戻って是正する」を追加した。
* **根拠**: 手順(1)の「範囲を狭めたと分かる書き方」が要である。要約を差し替えるだけでは、読み手が元の要求の広さを知る手段が無くなる。今回の `REQ-NFR-003` はまさにこの形で誤読を生んでいた。

## 3. 未充足は出荷への影響で評価する(`SKILL-P302-deliver.md`)

* **事象**(欠陥報告ではなく人間からの要望): 未充足のすべてが等しくリリースを妨げるわけではない。本番環境でしか検証できない要件や、実現が自明な要件がある。V1.0には状態語彙(検証できたか)しかなく、**出荷を妨げるかどうかを表す軸が無かった**。
* **V1.1での変更**: 対応表に **`出荷影響` 列を追加**した(状態列は現行のまま維持)。状態が `OK` 以外の行に、次のいずれかと**判断理由**を付す。

  ```text
  本番検証   本番相当環境でのみ検証可能。出荷は妨げないが稼働前に運用側での確認が必要
  代替検証   別のテストで実質的にカバーされている。カバーしているテストIDを必ず明記
  自明       構成上・実装上、成立が自明。根拠を必ず明記
  要対応     出荷に影響する。リリース前に対応または人間の判断が必要
  ```

  * リリース判定との接続: `要対応` が1件でもあれば判定を `OK` にしない。`本番検証`/`代替検証`/`自明` は理由が書かれている限り `NG`/`保留` の根拠に数えないが、10章には全件列挙する。判定根拠には `要対応` の件数と内訳を明記する。
  * 禁止事項に「判断理由を書かずに `本番検証`/`代替検証`/`自明` を付けない」「判定を `OK` にしたいがために `要対応` を他の値に付け替えない」を追加した。
* **根拠**:
  * **「検証できたか」と「出荷を妨げるか」を1列に混ぜないことが本変更の要**である。1列にまとめると、「出荷に影響しない」という判断が「検証済み」に見えてしまい、**テストしていないという事実そのものが失われる**。状態列を温存したまま軸を1本足す形にした。
  * 判定材料から外す仕組み自体は既存である。V1.0のL292は★ACCEPTED★付きの既知の制約について「既に判断済みの受容済みリスクであるため、11章の判定を `NG`/`保留` にする根拠には数えない」と既に規定していた。**V1.1はその判断基準を明示化するもの**であり、新しい抜け道を作るものではない。
  * 各値には**乱用の歯止め**を付けた。特に `自明` は根拠の記載が無い場合は使用禁止とし、「テストしていないが動くはず」は `自明` ではなく `要対応` であることを明記した。`本番検証` も「時間が無かった」「環境を用意できなかった」は該当しないと明記し、10章への引き継ぎを義務化して「判定から外して放置」を防いだ。

## 4. 識別子の表記ゆれをP010で検出する(`SKILL-P010-design-review.md`)

* **事象**: `V1.0_testbed` の全文書を機械照合したところ、**APIエンドポイントのパスパラメータ名が3リソースすべてで2通り併存**していた。
  * `/api/reservations/{id}` と `/api/reservations/{reservation_id}`、`/api/rooms/{id}` と `/api/rooms/{room_id}`、`/api/users/{id}` と `/api/users/{user_id}`。
  * **`docs/P002-frontend-spec.md` は同一文書内で矛盾**していた(本文は `{reservation_id}`、Mermaidシーケンス図は `{id}`)。`docs/P005-impl-plan.md` も同一文書内で両方を使っていた。
  * 機能上の実害は無いが、**P004・P302は行のキーとしてエンドポイント文字列を使う**ため、表記が2通りあると上記1の目的(要求IDと仕様IDの対応)が成立しない。
* **これは規定の欠落ではない**。V1.0のP010は「用語・命名の一貫性」と「図と本文の整合性(Mermaid図と本文が矛盾していないか。図は本文と乖離しやすい典型箇所)」を既にレビュー観点に挙げており、P002の事象は**まさに後者そのもの**だった。観点は揃っていたのに検出されなかった。
* **V1.1での変更**:
  * レビュー観点に **「識別子の表記の一貫性」** を独立項目として追加し、対象(APIエンドポイント(パスパラメータ名を含む)/画面ID/エラーコード/テーブル名・カラム名/P004・P302が表のキーに使う文字列)を具体的に列挙した。
  * **確認方法を「通読」ではなく「列挙と突き合わせ」と規定**した。対象を全文書から抜き出し、可変部分を伏せた形に正規化してグループ化し、同じ対象に2通り以上の表記が無いことを確認する。読んで気づくかどうかに頼らない。
  * **Mermaid図の中の識別子も対象**であることを明記した。
  * 重大度基準に例外を追加した。表記ゆれは原則 `低` だが、**P004・P302が表のキーとして使う識別子については `中`** とする(トレーサビリティが成立しなくなるため)。
* **根拠**: 抽象的な観点を、機械的に実行できる具体手順に置き換える形は本Skillに前例がある。V0.8の2-15は「テスト実行コマンドは記載前に一度実際に実行し、意図したテストが実行されることを確認する」という具体行動を課すことで、「コマンドが正しいか確認する」という抽象的指示では防げなかった不具合(0件が静かにスキップされる)を解消した。今回も構造は同じで、`{id}` と `{x_id}` の差は文書を順に読んでいるときには目に入らず、横断的な正規化とグループ化によってしか見えない。

## 5. リポジトリ直下 `README.md` への紹介パート追記

* **事象**: Skillに同梱される人間向け文書は `USER_GUIDE.md`(手順書)のみで、「これは何で、なぜこの作り方をするのか」を説明する文書が無かった。リポジトリ直下 `README.md` は版ごとの変更履歴が中心で、冒頭に短いコンセプト説明があるだけだった。
* **V1.1での変更**: 直下 `README.md` の冒頭に紹介パートを追記した(新規ファイルは作らない)。内容は次の3点と、**Step・Phaseと人間の介入ポイントを示すMermaid図**。
  1. **コンセプト**: ウォーターフォール/V字モデルの工程をClaude Codeに踏ませる。**Skill本体はコードを書かない**(指示書を生成し、それをClaude Codeが実行して初めてコードが書かれる)という構造を冒頭に置く。
  2. **役割分担**: 人間が関わるのは(a)最初の要求、(b)出来上がりの確認、(c)変更要求(CR)の3点だけ。フェーズごとに確認を求められることはなく、例外は停止条件に該当したときだけ。
  3. **なぜワンショットではないか**: 要求から直接コードを書かせると、テストもそのコードを見て書かれるため、**コードの誤解をテストがそのまま追認**し「テストは全部通るのに要求を満たしていない」状態が起きる。V字ではテストの根拠が実装ではなく上流文書になる(単体↔実装定義、結合↔詳細設計、受け入れ↔要件定義)。加えてP004・P302という抜け漏れを機械的に確認する工程がある。
* **根拠**: `USER_GUIDE.md`(どうやって)と重複させず、READMEは「何を・なぜ」に絞った。版の履歴は後段にそのまま残している。

## 6. 「省略できる手順が無いか」の検討結果

人間の指示により、**V1.0の手順のうち、省略しても最終品質に影響しないものが無いか**を検討した。**結論: 省略できる手順は見つからなかった。** V1.1でフェーズや手順を削る変更は行わない。

検討方法と結果は次のとおり。

* **成果物の依存グラフを総当たりで確認した。** 各フェーズの成果物が、他フェーズの「インプット文書」節に現れるかを機械的に照合したところ、**全フェーズの成果物が1つ以上の後続フェーズに消費されていた**。誰にも参照されない成果物を作っているフェーズは無い。
  * 唯一 `BUILD_HISTORY.md` だけがインプットに現れないが、これは中間成果物ではなく**人間が読むための納品物**であり(P302の品質基準「バージョン情報とビルド履歴の所在が明記されている」に対応)、消費されないことが正しい。
* **重複記述を検出した。** 45文字以上が完全一致する記述を全SKILLファイルから抽出したところ17件見つかったが、**いずれも姉妹フェーズの並行構造**であり、削除すると片方に穴が空く。
  * P002/P003(2つの設計フェーズ)、P008/P009(2つのテスト指示フェーズ)、P010/P201(2つのループフェーズ)、P103/P201(いずれもテストコードを新規作成しうるフェーズ)。
  * これらは `SKILL.md` の「各フェーズ共通指示」ではなく各フェーズ固有の規定であり、共通指示へ移すと「P103とP201の場合は〜」という条件付き規定の寄せ集めになって、かえって読みにくくなる。現状の並行構造が適切と判断した。
* **条件付きフェーズ・条件付き成果物**(P011/P012、`docs/ADR_master.md` など)は、条件に該当しなければ実行・作成されないため、そもそも省略の対象にならない。

この結果は予想と一致する。**V0.5以降の各版は、いずれも実地検証で見つかった具体的な不備に対応して追加されたもの**であり、投機的に足された手順が無い。裏を返せば、今後もこの検討を繰り返す価値は低い。次に検討すべきなのは、新しい手順を足すときに「既存のどれかで代替できないか」を都度確認することであり、事後に棚卸しすることではない。

## 7. V1.1で変更しなかった点

* **フェーズ構成・進め方は変更していない。** P番号体系、Step構成、連続実行の方針、停止条件のいずれにも手を付けていない。
* **上流文書(P001/P002/P003/P006)へのID体系導入は行っていない。** P001に `REQ-*` を振り、P002/P003が実現する要求を宣言する案を検討したが、11ファイル規模の変更になり、V0.7のCR3ファイル分離以来の大改造となる。人間の判断により、「P004・P302がID+要求の概要を併記しており、厳密な対応が取れていない点は許容する」として見送った。
* **状態語彙(10値)は変更していない。** 出荷影響は別列として追加しており、既存の `OK`/`BLOCKED`/`DEVIATED` 等の意味は変えていない。
* **★ACCEPTED★が付いた4論点の判断内容は変更していない。**
* **V0.7〜V1.0で確立した構造は維持している。** CR運用の3ファイル構成、タスク単位チェックボックス、`.inprogress` の入れ子表記、「テスト指示側の誤り」区分、停止時の対処案提示、テストスイートの再実行可能性。
* **既存プロジェクトへの遡及適用はしない。** V0.6以降の方針を維持する。
