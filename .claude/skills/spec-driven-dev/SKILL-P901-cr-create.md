# 変更要求作成

## 目的

* 納品後(またはPlan Loop Step完了後)にユーザーから寄せられた改善・修正の要望を、変更要求(CR)として `docs/P901-cr-direction/CR-NNN.md` に整理し、`docs/CR.md`(状態の台帳)に1行追加する。
* 要望は会話・issue・メールなど**任意の形式**で示されてよい。それを本フェーズがCRの形に整理するのであって、人間にファイルを書かせない。
* ここでは要求の整理のみを行い、設計・実装の修正はP902以降で行う。

## インプット文書

* ユーザーからの要望(会話・issue・メールなど、フォーマットは問わない)
* 既存の `docs/CR.md` (あれば。採番済みCRの状況確認)
* 既存の `docs/P901-cr-direction/` 配下のファイル (あれば。次の番号の採番のため)
* `docs/ArchitectureHandbook.md` / `docs/ADR.md` (影響範囲を見積もる参考として)

## アウトプット文書

* `docs/P901-cr-direction/CR-NNN.md` (変更要求1件につき1ファイル)
* `docs/CR.md` (状態の台帳に1行追加)

### アウトプットの記載内容

* 変更要求ファイルは `TEMPLATE-P901-cr-direction.md` の構成に則り、要望1件につき1ファイル作成する。複数の要望が混ざっている場合は分割し、それぞれ別のCR番号を与える。
* CR番号は **3桁**(`CR-001`)とする。既存のID体系(`U001`/`T001`/`A001`/`F001`/`ADR-001`)に合わせている。`docs/P901-cr-direction/` に既にあるファイルを見て、次の番号を採番する。
* 他の `P0NN-*-direction` と異なり、**目次ファイル `docs/P901-cr-direction.md` は作らない**。`docs/CR.md` が目次(一覧)の役割を兼ねるためである。
* 変更要求ファイルには、状態・優先度の現在値・対処内容を書かない。状態と優先度は `docs/CR.md` が、対処内容は `docs/P903-cr-records/CR-NNN.md` が持つ。
* `docs/CR.md` には、`TEMPLATE-CR.md` の一覧表の書式に従って行を追加する。追加時点の状態は `未対応`、対処記録列は `(未作成)` とする。`docs/CR.md` がまだ存在しない場合は `TEMPLATE-CR.md` にもとづいて新規作成する。
* 優先度は人間の指示があればそれに従い、なければ次のルーブリック(影響度×緊急度)にもとづいて仮置きし、変更要求ファイルの「優先度の判断理由」に理由を書いたうえで、その行(または直後の行)に "★FIXME★" を付けて人間の確認を促す。

  | | 緊急度: 高(今すぐ困っている/回避策がない) | 緊急度: 低(すぐには困らない/回避策がある) |
  |---|---|---|
  | **影響度: 高**(多くの利用者・主要機能に影響) | 優先度: 高 | 優先度: 中 |
  | **影響度: 低**(一部の利用者・周辺機能に影響) | 優先度: 中 | 優先度: 低 |

  * 「影響度」は、その変更要求が対象とする画面・API・利用者層の広さで判断する。
  * 「緊急度」は、対応しないことで発生している/発生しうる実害の大きさと、回避策の有無で判断する。
  * 機械的に表に当てはめるだけでは判断がつかない場合(例: 影響度・緊急度のどちらとも言えない)は、Agent自身の判断で妥当な優先度を選び、判断理由を書いたうえで★FIXME★を付ける。
* 既存の `docs/ADR.md` に抵触する要望(既に採用済みの決定を覆す要望)であれば、その旨を変更要求ファイルの「影響が想定される範囲」に明記する。
* 起票の時点で却下が決まっている場合は、`docs/CR.md` の状態を `却下`・**優先度を `N/A`** とし、`docs/P903-cr-records/CR-NNN.md` を本フェーズで作成して却下理由を記載する(`TEMPLATE-P903-cr-record.md` 参照)。却下されたCRは対応しないことが決まっているため、優先度の判断自体が不要になる(`TEMPLATE-CR.md` 参照)。
  * **これは意図的な例外である**: `docs/P903-cr-records/` はディレクトリ名のとおり通常はP903が作成するが、起票時点で却下が決まっているCRはP903に到達しない(P902以降が実行されない)ため、却下を決めたP901がこのディレクトリに直接ファイルを作成する。「どの節をどのフェーズが書くかは固定」という原則自体は変えておらず、却下ケースに限り担当フェーズがP901になるという例外を明記したものである。

### アウトプットを参照する文書

* `docs/P902-*` (要件定義更新) が、`docs/P901-cr-direction/CR-NNN.md` の内容にもとづき `docs/P001-requirement.md` を更新する。
* `docs/P903-cr-records/CR-NNN.md` (P903がスコープ決定の対象として参照する)
* P904が「期待する振る舞い」を1項目ずつ確認する。

## 動作

* 共通指示以外は特になし
* 作成した変更要求ファイルは、人間が後から内容を修正してよい。ただし `docs/CR.md` の状態が `対応中` に移った以降は変更しない(作業の前提が動くため)。それ以降に変えたい点が出た場合は、新しいCRを起票する。
* 本フェーズはRefactor(修正)のみで実行される、Plan Loop Step / Executor / Reviewer Loop / Closing の各Stepでは実行しない。
