## ADR-001 — Excel の用法を判別せず、両方の Markdown を常に出力する

**状態**: 採用 / **決定日**: 2026-08-24 / **関連要求**: REQ-F-064〜068

**文脈**: Excel には「正規の表計算として使う」用法と「セルを方眼紙にして文書を組む」用法があり、適切な Markdown 表現がまったく異なる。1つのブック内で両方が混在することもある。

**決定**: **用法の判別を行わない。** 表計算モード (`{ステム}.table.md`) と方眼紙モード (`{ステム}.grid.md`) の**両方を常に生成する**。どちらを採用するかは後段の RAG パイプラインに委ねる。

**理由**:

1. 判別を誤ると本来得られたはずの情報が完全に失われ、**しかも失われたことを後段から検知できない** (誤った表が1つ出力されるだけで、欠落が見えない)。
2. 判別ロジックの閾値 (結合率・列幅・数値セル比率) は組織ごとの文書作法に強く依存し、汎用的な正解値が存在しない。
3. シートごとに用法が異なる場合、判別の誤りが局所的に散在して発見がさらに困難になる。

**結果**: Excel については出力ファイル数と総文字数が約2倍になる。この重複は front matter の `output_mode` フィールドで後段が識別・選別できる。`--excel-modes` で片方に限定する逃げ道も用意した。

**却下した案**: セルの特徴量から自動判別して片方だけ出力する / 1ファイルに両表現を並べて格納する (同一文書内に近似重複が生じ、チャンク検索結果が同じ内容で埋まる)。

## ADR-002 — 数式のキャッシュ値の判定を openpyxl + lxml のハイブリッドで行う

**状態**: 採用 / **決定日**: 2026-08-24 / **関連要求**: REQ-F-051, REQ-F-068 / **根拠**: 実測 (P003 §1.2)

**文脈**: `.xlsx` は数式セルについて「数式」と「Excel が最後に計算した結果 (キャッシュ値)」を持つ。機械生成されたファイルはキャッシュ値を持たず、値だけを取り出すとセルが黙って空になる。両方を取得する必要があるが、REQ-F-068 は「解析は1回のみ」を求める。

**決定**: **openpyxl を `data_only=True` で1回ロードし、加えて sheet XML に対する lxml の1パスを併用する。**

* openpyxl が担当: セル値・表示形式・結合範囲・非表示属性
* lxml が担当: 数式文字列と、キャッシュ値の有無

**理由**: 実測により次を確認した (200行20回の平均)。

| 方式 | 所要 |
| --- | --- |
| openpyxl 1回ロード | 5.07 ms |
| openpyxl 2回ロード (`data_only` 切替) | 10.10 ms (**1.99倍**) |
| lxml で sheet XML を1パス | 2.36 ms |

ハイブリッドの合計は約 7.4 ms で、2回ロード方式より**約27%速い**。図形抽出でどのみち同じ ZIP を開くため、統合できる。

**結果**: 同じシートを2経路で読むため、両者のセル座標の対応付けにずれがあると値と数式が食い違う。座標を1起点に統一し、突合をセル参照文字列で行うことで防ぐ。

**却下した案**: openpyxl を2回ロードする (実測で正確に2倍。REQ-F-068 の趣旨に反する) / 全て lxml で読む (共有文字列・表示形式・スタイル継承の自前実装が割に合わない)。

**実装上の必須知識**: `docs/ArchitectureHandbook.md` §9-1 を参照。**`<v>` 要素の有無で判定してはならない。**

## ADR-003 — `mc:AlternateContent` は `mc:Choice` のみを辿る

**状態**: 採用 / **決定日**: 2026-08-24 / **関連要求**: REQ-F-031 / **根拠**: 実測 (P003 §1.3)

**文脈**: Word のテキストボックスは `mc:AlternateContent` の下に、`mc:Choice` (新形式 `wps:txbx`) と `mc:Fallback` (旧 VML `v:textbox`) の**両方に同じ内容**を持つ。

**決定**: `mc:AlternateContent` に遭遇したら配下を直接走査せず、**最初の `mc:Choice` のみ**を辿る。`mc:Choice` が無い場合に限り `mc:Fallback` を辿る。この選択を再帰の各階層で行う。

**理由**: 実測により、素朴な `.//w:txbxContent` の全件検索が**同じテキストを2件返す**ことを確認した。

```
素朴な走査:     txbxContent 2 件 → ['図形の1段落目図形の2段落目', '図形の1段落目図形の2段落目']
Choice優先走査: txbxContent 1 件 → [['図形の1段落目', '図形の2段落目']]
```

これを怠ると、**本アプリの中核機能である図形テキストがすべて2回ずつ出力される**。

**結果**: `mc:Choice` が複数ある場合は `Requires` 属性が `wps`/`wpg` のものを優先する。未知の拡張しか無い場合はテキストが取れないことがあるが、現行の Office では生じない。

## ADR-004 — 中間表現は結合セルを展開せず、複製の有無をレンダラの責務とする

**状態**: 採用 / **決定日**: 2026-08-24 / **関連要求**: REQ-F-030, REQ-F-062 / **不変条件**: INV-09

**文脈**: 表計算モードは結合セルの値を範囲内の全セルに**複製**してテーブルの矩形を保つ。方眼紙モードは**1回だけ**出力する (複製すると同じ文言が反復してノイズになる)。**扱いが正反対**である。

**決定**: 中間表現 `Sheet` は**結合を展開しない**。`Cell` は結合範囲の左上にのみ存在し、範囲情報は `merged` に別途保持する。複製するか否かはレンダラが決める。

**理由**: 展開済みのテーブルを中間表現とすると、方眼紙モードのレンダラが**複製を取り除けない** (どれが元でどれが複製か区別できない)。展開しない形なら、表計算モードが複製し、方眼紙モードは何もしないだけで済む。

**結果**: `Sheet` 構造が他形式のブロックより情報量が多く、非対称になる。この非対称は、Excel だけが「1つの解析結果から2つの表現を作る」という要件を持つことに由来する。

**却下した案**: Excel については中間表現を2つ (テーブル用・本文用) 持つ (パーサが2回走るか、1回で2構造を組み立てることになり、REQ-NF-011 の「共通の中間表現を経由する」構造から外れる)。

## ADR-005 — 並列の粒度を1入力ファイルとし、Excel の二重出力を分割しない

**状態**: 採用 / **決定日**: 2026-08-24 / **関連要求**: REQ-NF-015, REQ-F-068

**決定**: `ProcessPoolExecutor` による**ファイル単位**の並列とする。Excel の2つの出力を別ワーカーに分けない。ワーカー関数はモジュールのトップレベルに置く。

**理由**: 二重出力を分割すると、同じ中間表現を2プロセスに渡すことになり、解析が二重になって REQ-F-068 に反する。また `Document` の pickle コストが変換自体を上回る。

**結果**: ワーカーからは書き出したパスと警告のみを返し、`Document` や `ConversionResult` を返さない。Windows は `fork` を持たず `spawn` を使うため、ワーカー関数はトップレベル定義でなければならず、CLI エントリポイントは `if __name__ == "__main__":` で保護する必要がある。

## ADR-006 — SmartArt はデータモデルを採用し、描画結果を読まない

**状態**: 採用 / **決定日**: 2026-08-24 / **関連要求**: REQ-F-034

**文脈**: SmartArt は `diagrams/data*.xml` (データモデル) と `diagrams/drawing*.xml` (描画結果) の**両方に同じテキスト**を持つ。

**決定**: **データモデル側 (`data*.xml`) のみを読む。** 描画結果側は走査しない。

**理由**: データモデルはノードの親子関係 (`dgm:cxnLst` の `parOf`) を保持しており、箇条書きの階層を再現できる。描画結果側は階層が失われている。両方を読むと二重出力になる。

**結果**: レイアウト種別によっては階層が正しく取れない可能性がある。その場合はすべて `level=0` のフラットな箇条書きに落とし、例外を送出しない。

## ADR-007 — openpyxl を `read_only=False` で開く

**状態**: 採用 / **決定日**: 2026-08-24 / **関連要求**: REQ-F-030, REQ-NF-003

**決定**: メモリ効率で劣る `read_only=False` を選ぶ。

**理由**: `read_only=True` は結合範囲 (`merged_cells`) にアクセスできず、REQ-F-030 (結合セルの複製) を実装できない。機能要件を優先した。

**結果**: 巨大ファイルでのメモリ使用量が増える。`--max-rows` (既定 10,000) による打ち切りが緩和策として働く。

## ADR-008 — 変換結果のキャッシュを持たない (ステートレス)

**状態**: 採用 / **決定日**: 2026-08-24 / **関連要求**: REQ-NF-018

**決定**: 永続化データストアを一切持たない。変換結果のキャッシュも持たない。状態はプロセス内メモリのみ。

**理由**: (a) キャッシュの保存先・無効化・容量管理という複雑さが生じる、(b) RAG パイプライン側が既に「取り込み済みか」を管理していることが多い、(c) front matter の `source_sha256` を出力しているため**再変換の要否判定は利用者側で行える**。

**結果**: 同じファイルを繰り返し変換する使い方では毎回フルに処理する。**データストアを持たないため、スキーマのマイグレーションという概念が存在しない** (P003 §3.1)。将来キャッシュを導入する場合は、バージョン管理テーブルで差分適用する方式を採ること (全件再実行方式は `ALTER TABLE ADD COLUMN` が加わった時点で破綻する)。

## ADR-009 — `ConversionResult.markdown` は複数出力時に例外を送出する

**状態**: 採用 / **決定日**: 2026-08-24 / **関連要求**: REQ-F-102

**決定**: 出力が1件のときのみ `markdown` プロパティで本文を返す。**2件以上 (Excel の二重出力) では `ValueError` を送出する。**

**理由**: 「先頭を返す」実装だと、Excel を渡した利用者が黙って表計算モードだけを受け取り、**方眼紙モードの出力を取りこぼす**。取りこぼしを黙って起こすより、明示的に失敗させる方を選ぶ。

**結果**: Word のみを想定していた既存の利用コードが Excel を渡された際に `ValueError` で落ちる。これは意図した挙動であり、API ドキュメントに明記する。複数出力を扱う利用者は `outputs` を参照する。

## ADR-010 — Markdown のエスケープを行頭の構造記号のみに限る

**状態**: 採用 / **決定日**: 2026-08-24 / **関連要求**: REQ-F-009

**決定**: 行頭の `#` `-` `*` `+` `>` `数字.` ` ``` ` と、テーブルセル内の `|` のみをエスケープする。**行中の `*` `_` `` ` `` `[` `]` はエスケープしない。**

**理由**: CommonMark 上はこれらも強調やリンクと解釈されうるが、日本語文書では `_` を含む識別子や `*` を含む注記が頻出し、全エスケープすると本文がバックスラッシュだらけになって**埋め込み品質を落とす**。実害は稀な誤強調に留まる。

**結果**: 本文中に `*強調風の記述*` があると強調として解釈される。

## ADR-011 — CLI とライブラリの UI を分離し、Web UI を作らない

**状態**: 採用 / **決定日**: 2026-08-24 / **関連要求**: P001 §1.4

**決定**: 利用者インタフェースは CLI (Typer + Rich) と Python ライブラリ API の2つとする。**Web UI を提供しない。**

**理由**: 主用途が RAG パイプラインへの組み込みであり、CLI とライブラリ API で充足する。HTTP サーバを持たないため、認証・TLS・CORS・クロスオリジンの検討がすべて不要になり、設計と運用が単純になる。

**結果**: 非エンジニアが単独で使うにはコマンドライン操作の習得が必要。将来 Web UI を追加する場合は、クロスオリジン方針を新たな ADR として記録する必要がある。

## ADR-013 — タグ付きか否かを構造ツリーの被覆率で判定し、タグなしは構造を推定しない ※CR-001

**状態**: 採用 / **決定日**: 2026-10-14 / **関連要求**: REQ-F-111〜116

**決定**: 次の2つを満たす PDF をタグ付きとして扱い、構造ツリーの順序で見出し・リスト・表・段落・図に写す。

* 構造ツリーを持つ。
* 空白以外の本文文字の **50% 以上**が構造要素に属する。

この条件を満たさない PDF はタグなしとして扱い、見出しやリストを推定せずに段落の並びとして出力する。構造ツリーを持つのに被覆率が足りない場合は警告を出す。

**理由**: タグ付けが不完全な PDF を構造どおりに出すと、構造に入っていない本文が大量に失われる。一方で見出しを推定すると、誤ったときにチャンク境界まで誤る。依頼者も、論理構造が無ければ単純なテキストの羅列にするよう指示し、見出しの推定は不要と明言している。

**結果**: 被覆率が 50〜100% の PDF では、構造に入っていない本文 (最大で半分) が出力されない。出力されなかった行数は `stats.headers_footers_removed` に含めて見えるようにしている。タグなし PDF の出力には見出しが付かない。

## ADR-014 — タグなし PDF の補正を、帯の繰り返し判定と段間優先の段組み検出で行う ※CR-002

**状態**: 採用 / **決定日**: 2026-10-14 / **関連要求**: REQ-F-122〜128

**決定**:

* **ヘッダー・フッター**: ページ上下 10% の帯にあるテキストを数字を `#` に正規化して数え、2ページ以上かつ全ページの 30% 以上に現れたものを除去する。`--headers-footers` を指定したときは除去しない。
* **段組み**: 先に段間 (縦の空白) を確定し、段抜き要素でページを区間に分ける。区間ごとに、左の段から順に各段を上から下へ読む。
* タグ付き PDF にはどちらも適用しない。タグ付きでは `Artifact` の除外と構造ツリーの順序を使う。

**理由**:

1. 奇数・偶数ページで異なるヘッダーは、それぞれ出現率が約 50% になる。閾値を 30% にしてこれを拾う。
2. 1ページしかない文書や1回だけ現れるテキストを残すのは、本文を誤って消す害のほうが、ノイズを残す害より大きいからである。
3. 再帰的な XY-cut は行間の空白で横に切れてしまい、左右の段の行が交互に並ぶことがある。これは CR-002 が直したい症状そのものなので採らなかった。

**結果**: 罫線の無い表は段組みとみなされ、列ごとに読まれることがある。帯の中で繰り返される本文 (定型の注意書きなど) も除去される。縦書きは対象外である。

## ADR-015 — PDF の読み取りに pdfminer.six (MIT) を用い、依存を `pdf/backend.py` に閉じ込める ※CR-003

**状態**: 採用 / **決定日**: 2026-10-14 / **関連要求**: REQ-F-110〜128, REQ-NF-019〜021 / **根拠**: 実測 (P003 §1.5、`docs/research/pdf-library-alternatives.md`) / **置き換えた ADR**: ADR-012 (廃止。`docs/ADR_master.md`)

**文脈**: CR-001 では依頼者の指示で PyMuPDF (AGPL-3.0) を暫定的に採用した (ADR-012)。依頼者は本アプリの MIT を保つことを求めており、代替を検討した結果、Docling は代替にならず、PDF Inspector は単独では代替にならず、pdfminer.six (MIT) は必要な情報をすべて取れた。

**決定**: PDF の読み取りに **pdfminer.six** を用いる。PDF ライブラリを import してよいのは `pdf/backend.py` のみとする (ADR-012 の閉じ込めの方針を継承)。**実行時依存は MIT と両立するライセンスに限り、受け入れテスト (A007) で常に検査する** (REQ-NF-021)。

**理由**:

1. マーク付きコンテンツを文字ごとに受け取れるため、MCID と Artifact を内容ストリームのとおりに判別できる。PyMuPDF で要った補正 (構造の後の Artifact) が不要になり、MCR 辞書形式のタグ付き PDF も構造どおりに変換できる。
2. 構造ツリー・属性・図形・暗号化・権限・生ストリームを、すべて取得できる。
3. 純 Python で外部バイナリを要さない。依存 (cryptography・charset-normalizer) も MIT と両立する。

**結果**: 文字抽出は PyMuPDF の約 9 倍の時間がかかる (50ページで 1 秒未満の見込み)。近接する図形のまとめを自前で持つ (`pdf/drawings.py`)。pdfminer.six は描画順に文字を返すため、構造木を `/K` の順に並べ直す処理を持つ (P003 §7A.3)。

**却下した案**: PyMuPDF の継続 (AGPL-3.0)、Artifex の商用ライセンスの取得 (費用と、MIT で配布できない点は変わらない)、Docling (タグを使わず、モデルのダウンロードを要する)、PDF Inspector の単独使用 (構造の階層・属性・図形が取れない)。
