このアプリケーションの技術的側面をまとめたハンドブック。**実装・改修を担当する者が、設計書一式を読み直さずに全体像と落とし穴を把握するための文書**である。

## 1. このアプリは何をするか

Office 文書 (Word / Excel / PowerPoint) を、**RAG パイプラインが取り込むための Markdown** に変換する CLI ツール兼 Python ライブラリ。

読み手は人間ではなく**チャンク分割器と埋め込みモデル**である。したがって視覚的忠実性 (フォント・色・配置) を捨て、**構造的忠実性** (見出し階層・表・シート/スライド境界・図形内の文言) を追う。

### 他ツールと異なる2点

1. **オートシェープ内テキストを取りこぼさない** — 日本のビジネス文書は要点や注意事項が図形の中に書かれていることが多く、既存ツールの多くはこれを落とす。OCR は使わず、OOXML 上のテキストを回収する。
2. **Excel の二面性に判別なしで両対応する** — 「表計算」か「方眼紙」かを判別せず、両方の Markdown を常に出力する (ADR-001)。

## 2. アーキテクチャの骨格

```
入力ファイル → detect_format → 形式別パーサ → 中間表現 Document → レンダラ → MarkdownOutput × 1〜2 → ファイル
                                     ↑
                          ShapeTextExtractor (3形式で共有)
```

**三層構成** (パーサ / 中間表現 / レンダラ) を貫く。**Excel だけが「1つの中間表現から2つのレンダラが動く」**。これが本アプリの設計上の要である。

### 依存の方向 (厳守)

```
cli/  →  convert.py / batch.py / inspection.py / config.py
              ↓
        parsers/  →  ooxml/
              ↓
          models/   ←  render/
```

* `models/` は**他のどの層にも依存しない**。
* `render/` は `models/` **のみ**に依存する (`parsers/` `ooxml/` を import しない)。
* `parsers/` は `render/` を知らない。

この一方向依存により、**レンダラの単体テストがパーサなしに書ける** (中間表現を直接組み立てる)。テスト設計はこれを前提としている。

## 3. 中間表現の要点

| 型 | 役割 |
| --- | --- |
| `Document` | 形式非依存。`blocks` の並びが**そのまま出力順**になる (INV-04) |
| `Block` のバリアント | `Heading` / `Paragraph` / `ListBlock` / `Table` / `ShapeText` / `Image` / `Footnote` / `SlideBreak` / **`Sheet`** |
| **`Sheet`** | **Excel 専用。他形式より情報量が多い**。セルの生データ・結合範囲・検出済み表領域・図形を保持する |
| `Document.images` | 抽出した画像バイナリ。**中間表現が1つであるため、Excel の二重出力でも画像が重複しない** (REQ-F-069) |

### `Sheet` が特別な理由

表計算モードは結合セルを**複製**し、方眼紙モードは**1回だけ**出力する。扱いが正反対であるため、**中間表現は結合を展開せず範囲情報のまま持つ** (ADR-004 / INV-09)。展開済みのテーブルを持つと、方眼紙モードが複製を取り除けない。

### 守るべき不変条件

| # | 条件 | 破ると何が起きるか |
| --- | --- | --- |
| INV-02 | `InlineRun.text` は**エスケープ前**の生文字列 | 二重エスケープでバックスラッシュが増殖する |
| INV-03 | 空の `InlineRun` を作らない | 冪等性比較のノイズになる |
| INV-04 | `blocks` の順序 = 出力順 (脚注と位置不明図形のみ末尾へ移送) | 出力順が実行ごとに変わる |
| **INV-07** | `Sheet.rows` は**空行も含めて**行番号順に欠番なく持つ | 方眼紙モードの段落境界が壊れる |
| **INV-08** | `SheetRow.cells` は列番号昇順・非空セルのみ | 方眼紙モードの連結順が乱れ、文が壊れる |
| **INV-09** | **結合を展開しない** | 方眼紙モードで同じ文言が反復出力される |
| INV-10 | `Sheet.regions` は最低1要素 (空シートを除く) | レンダラの分岐が壊れる |
| INV-11 | `regions` どうしが重ならない | 同じセルが複数テーブルに現れ、重複チャンクが生じる |

## 4. 実装時に踏んではならない落とし穴 (実測で確認済み)

**この節は P003 §1 のスパイクで実際にコードを走らせて確認した事実である。推測ではない。**

### 4-1. openpyxl は空の `<v>` を書き出す

数式セルの生 XML は次のようになる。

```xml
<c r="B2"><f>A2*2</f><v></v></c>
```

**`<v>` 要素は存在するが中身が空**である。したがって:

* ❌ `if v_element is None:` でキャッシュ値なしを判定 → **必ず誤判定する**
* ✅ `if v is None or v.text in (None, ""):` で判定する

誤ると、キャッシュ値の無いファイルで**空文字がセル値として出力され、数式が失われる** (要求②が機能しない)。

また **XML の `<f>` は先頭の `=` を含まない** (`A2*2`) が、openpyxl の `cell.value` は含む (`=A2*2`)。lxml 経路で得た数式は `=` を前置して正規化すること。

### 4-2. 素朴な図形走査は同じテキストを2回拾う

Word のテキストボックスは `mc:AlternateContent` の下に `mc:Choice` (新形式) と `mc:Fallback` (旧 VML) の**両方に同じ内容**を持つ。

```
素朴な走査 (.//w:txbxContent):  2件 → ['図形の1段落目図形の2段落目', '図形の1段落目図形の2段落目']
Choice優先走査:                 1件 → [['図形の1段落目', '図形の2段落目']]
```

* ❌ `root.findall(".//{...}txbxContent")` で全件取得
* ✅ 階層を辿る再帰で、`mc:AlternateContent` に遭遇したら `mc:Choice` のみを辿る

誤ると**すべての図形テキストが2回ずつ Markdown に出力される** (中核機能の品質が損なわれる)。

### 4-3. python-docx の公開 API では図形テキストが取れない

テキストボックスを含む段落に対し `document.paragraphs` が返すのは `['通常の段落です。', '']` — **図形内の文字列は空文字として落ちる**。lxml による直接走査の併用は必須である。

### 4-4. SmartArt は2箇所に同じテキストを持つ

`diagrams/data*.xml` (データモデル) と `diagrams/drawing*.xml` (描画結果) の両方にある。**データモデル側のみを読む** (ADR-006)。両方読むと二重出力になる。データモデル側は階層情報も持つ。

### 4-5. Excel のシート番号とファイル名は一致しない

`sheet1.xml` の `1` はシートの並び順ではない (削除・並べ替えの履歴による)。**`_rels` で関係 ID から解決すること**。ファイル名の数値で対応付けると、誤ったシートに図形が付く。

### 4-6. Excel の drawing アンカーは0起点

`xdr:from/xdr:col` と `xdr:row` は**0起点**である。A1 形式のセル参照にするには `+1` してから変換する。

### 4-7. Windows の `spawn` はローカル関数を pickle できない

`ProcessPoolExecutor` のワーカー関数は**モジュールのトップレベル**に定義すること。加えて CLI エントリポイントを `if __name__ == "__main__":` で保護しないと、ワーカーが再帰的に CLI を起動する。

## 5. Excel の二重出力の仕組み

```
ExcelParser (解析は1回のみ)
   ↓
Document(blocks=(Sheet, Sheet, ...))
   ↓                    ↓
ExcelTableRenderer   ExcelGridRenderer
   ↓                    ↓
{ステム}.table.md   {ステム}.grid.md
```

| | 表計算モード | 方眼紙モード |
| --- | --- | --- |
| ファイル | `{ステム}.table.md` | `{ステム}.grid.md` |
| `output_mode` | `table` | `grid` |
| 本文 | 表領域ごとの GFM テーブル | セルを列順に連結した本文 |
| 結合セル | **範囲内に複製する** | **左上を1回だけ** |
| 空行 | (テーブルの外) | **空行として出力 = チャンク境界** |
| `stats` | `tables` を含む | **`lines` を含み `tables` を含まない** |
| 図形テキスト | **章の末尾** | **章の末尾 (同じ内容・同じ位置)** |

**方眼紙モードのレンダラは結合セルについて何もしない。** 中間表現が既に望ましい形 (左上のみ) になっているため (INV-09)。ここが両モードの差の中心である。

### 表領域の検出 (要求①)

1. 使用範囲を求める
2. **完全に空の行**で水平分割
3. **各行ブロック内で**完全に空の列を垂直分割 (使用範囲全体で列判定すると分割が効かない)
4. 実データの範囲までトリミング
5. 上から下・左から右に整列
6. **領域数が上限 (既定100) 超なら分割を破棄**して1領域にし、警告を出す

**結合セルの非空判定**: 結合範囲に含まれるセルは、範囲の左上に値があれば**範囲全体を非空とみなす**。これがないと、複数列にまたがる結合見出しの行が空行と判定され、表が不当に分割される。

**上限の安全弁が必要な理由**: 方眼紙シートを表計算モードで処理すると非空セルが散在し、数百〜数千の微小領域が生じて Markdown が実用にならない。この場合は1つの大きな表として出力し、意味のある表現は方眼紙モード側が担う。

## 6. セキュリティの実装

| 対象 | 実装 | 場所 |
| --- | --- | --- |
| XXE / 十億の笑い | `resolve_entities=False`, `no_network=True`, `load_dtd=False`, `huge_tree=False` | `ooxml/xml_utils.py` の `safe_parser()` **のみ** |
| ZIP 爆弾 | 展開後サイズ (入力の200倍 or 1GiB の小さい方)、単一エントリ 512MiB、圧縮率 1000、エントリ数 10,000 | `ooxml/zip_reader.py` |
| パストラバーサル | 絶対パス・`..`・ドライブレターを含むエントリ名を拒否。`_rels` の Target 正規化後もルート外を拒否 | 同上 |
| マクロ | `keep_vba=False`。VBA パートを読まない | `parsers/excel.py` |
| 外部通信 | `no_network=True`, `keep_links=False`。**変換中に一切通信しない** | 各所 |

**規約**: XML のパースは必ず `xml_utils.parse_xml` を、ZIP は必ず `SafeZipReader` を経由する。各モジュールが `etree.fromstring` や `zipfile.ZipFile` を直接呼ばない。**これを破ると防御が素通りになる。**

## 7. 冪等性の担保

同一入力・同一オプションから、`converted_at` を除いて完全に同一の出力を得る (REQ-NF-018)。危険な要素と対処:

| 危険 | 対処 |
| --- | --- |
| 辞書・セットの反復順 | 出力順の決定に `set` を使わない。明示的にソートするか出現順を保つ `list` |
| ファイルシステムの走査順 | パス文字列でソート |
| 並列実行の完了順 | `as_completed` の結果を**入力順に並べ替えてから** `BatchResult` に入れる |
| 画像の連番 | **表計算モードでの出現順**で固定 |
| 浮動小数の文字列化 | 表示形式の適用結果を使い、`repr()` に頼らない |
| 現在時刻 | **`DocumentMeta` の生成箇所1箇所のみ**で取得。パーサ・レンダラの内部で `datetime.now()` を呼ばない |

比較時は `--no-front-matter` を使うか、`strip_front_matter()` で front matter を除いてから比較する。

## 8. ログの方針

* 出力先は**標準エラー**。標準出力は変換結果 (`--stdout`) と結果サマリのために空けておく。
* ロガーは `office2ragknowledge` 名前空間。**ハンドラの設定は CLI 層のみ**。ライブラリ側は `NullHandler` だけを付ける (import した利用者の設定を壊さないため)。
* **本文テキスト (セル値・段落・図形テキスト・title・author) をログに出さない。** 出してよいのはパス・件数・シート名・エラーコード。

## 9. 既知の制約・技術的負債

各項目は「何を検討したか」「なぜ採らなかったか」「残存リスク」を自己完結して含む。

### 9-1. 共有数式のセル参照が調整されない ★ACCEPTED★

**検討**: `<f t="shared">` の参照セルについて、相対参照を各セル向けに再計算して正しい数式を復元する案。
**不採用の理由**: A1 形式の相対/絶対参照の解析と再構成が必要で実装量が大きい。キャッシュ値の無いファイルでのみ表示される情報であり、「そこに数式がある」ことが判れば RAG の用途には足りる。
**残存リスク**: 共有数式のセルには先頭セルの数式がそのまま表示され、セル参照がずれて見える。

### 9-2. 通貨・会計書式の記号が抽出できないことがある ★ACCEPTED★

**検討**: `number_format` の書式文字列を完全に解析してロケール依存の通貨記号 (`[$¥-411]` 等) を抽出する案。
**不採用の理由**: 書式文字列の文法が複雑で、網羅には見合わない実装量が要る。
**残存リスク**: 記号が抽出できない場合、数値のみが出力される。金額であることが文脈から失われる可能性がある。

### 9-3. 図形プリセットの分類が網羅的でない ★ACCEPTED★

**検討**: Office が持つ全プリセット (180種類以上) を日本語名に分類する案。
**不採用の理由**: 分類表の保守コストに対して、RAG の検索品質への寄与が小さい。
**残存リスク**: 未分類のプリセットは総称「図形」として出力される。機能上の欠落 (テキストの取りこぼし) は生じない。

### 9-4. SmartArt の階層が取れないレイアウトがありうる ★ACCEPTED★

**検討**: レイアウト種別 (組織図・循環・リスト等) ごとに `dgm:cxnLst` の解釈を切り替える案。
**不採用の理由**: レイアウト種別の網羅が困難で、誤った階層を出すより平坦な方が害が小さい。
**残存リスク**: 階層が復元できない場合、すべて `level=0` のフラットな箇条書きになる。ノードのテキスト自体は失われない。

### 9-5. グラフの数値データを出力しない ★ACCEPTED★

**検討**: `c:val` の数値系列をテーブル化する案。
**不採用の理由**: RAG の検索単位としては系列名・カテゴリ名までで十分に索け、出力量が肥大する。
**残存リスク**: グラフ中の具体的な数値は Markdown に現れない。

### 9-6. 画像内の文字は抽出されない (OCR 非対応) ★ACCEPTED★

**検討**: OCR エンジンの同梱。
**不採用の理由**: 利用者から明示的に不要と示された。外部バイナリとモデルデータ (数百MB) が配布を著しく重くし、日本語 OCR の誤認識が検索ノイズになる。
**残存リスク**: 画像として貼り込まれた図表内の文言は Markdown に現れない。代替テキストのみが手掛かりとなる。

### 9-7. 旧バイナリ形式 (.doc/.xls/.ppt) に非対応 ★ACCEPTED★

**検討**: LibreOffice をヘッドレス起動して OOXML に変換する前処理。
**不採用の理由**: 外部アプリケーションへの依存が発生し、オフライン動作要件とコンテナ肥大化に反する。
**残存リスク**: 旧形式は利用者が事前に変換する必要がある。CLI が明示的なエラー (E-002) で案内する。

### 9-8. ログにシート名が現れる ★ACCEPTED★

**検討**: 機微情報の観点からシート名も伏せる案。
**不採用の理由**: どのシートで打ち切りやキャッシュ値欠落が起きたか判らない警告は用をなさない。シート名は本文テキストではなく構造の識別子として扱う。
**残存リスク**: シート名自体が機微な語を含む場合、それがログに残る。

### 9-9. `read_only=False` によるメモリ使用量 ★ACCEPTED★

**検討**: openpyxl の `read_only=True` によるメモリ削減。
**不採用の理由**: 結合範囲が取得できず、結合セルの複製 (REQ-F-030) を実装できない。
**残存リスク**: 巨大ファイルでメモリ使用量が増える。`--max-rows` (既定10,000) が緩和策。

### 9-10. Excel の出力量が約2倍になる ★ACCEPTED★

**検討**: 用法を自動判別して片方のみ出力する案 (ADR-001 参照)。
**不採用の理由**: 判別を誤ると情報が失われ、しかも失われたことを検知できない。
**残存リスク**: Excel の出力ファイル数と総文字数が約2倍。`output_mode` による選別と `--excel-modes` による限定で緩和する。

### 9-11. 性能・メモリの実測値が未取得

**状態**: 目標値 (1ファイル10秒、バッチ劣化1.5倍、50MBで2GB) は設定済みだが、**実測は P103・P201 で行う**。現時点では見積りである。
**対処**: P103 の計測結果を本節に追記すること。

### 9-12. Python 3.11 での動作が未確認

**状態**: 3.14.2 では依存6件すべての動作を実測で確認済み。**3.11 は未確認**。
**対処**: P201 の A004 項目14 で確認する。実行環境が用意できない場合は NOT RUN として記録し、対応範囲の記述を見直す。

## 10. よくある改修とその影響範囲

| やりたいこと | 触る場所 | 注意 |
| --- | --- | --- |
| 新しい図形種別を日本語名に分類したい | `ooxml/shapes.py` の `classify_shape` + P002 §5.8 の表 | 未分類は「図形」に落ちるだけなので影響は局所的 |
| 図形ブロックの体裁を変えたい | `render/shapes.py` + P002 §5.7 | 3形式すべてに波及する。ゴールデンファイルの更新が要る |
| 方眼紙モードの連結規則を変えたい | `render/excel_grid.py` + P002 §5.6 | **利用者が明示指定した仕様であるため、変更は CR (P901) を要する** |
| 表領域の検出規則を変えたい | `parsers/excel_regions.py` + P002 §5.4.2 + P003 §7.4 | 境界条件のテストが多数あるため、テストの期待値も見直す |
| 新しい形式 (例: `.odt`) を追加したい | `detect.py` に判定を追加 → `parsers/` に新パーサ → `render_document` に分岐 | 中間表現は変えずに済むはず。変える必要があれば設計の見直しを疑う |
| front matter に項目を足したい | `models/document.py` の `DocumentMeta` + `render/frontmatter.py` + P001 §7.1 | **キー順は冪等性のため固定**。末尾に足すこと |
| 出力ファイル名を変えたい | `render/__init__.py` + `writer.py` + P002 §5.2 | RAG 側の再取り込み判定に影響する。★FIXME★ が P001 §3.2 に残っている |
