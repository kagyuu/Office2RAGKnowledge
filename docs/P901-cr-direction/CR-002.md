# CR-002 — PDF のページヘッダー・フッターを除去し、段組みの読み順を補正する

## 起票日

2026-10-14

## 起票者

* HONDOH Atsushi (本アプリのオーナー)。Claude Code セッションでの口頭依頼 (2026-10-14)。CR-001 の起票内容に対する追加要望。
* 依頼原文: 「やらないことのうち、見出しの推定はやらなくていいです。ヘッダーフッターの除去はやってください。段組みの読み順の補正も行ってください。分けたほうが良ければ CR-2 を起こしてください。」

## 背景・課題

* [CR-001](./CR-001.md) で PDF を入力形式に追加する。ただし CR-001 だけでは、PDF のページから取り出したテキストを描画順またはページ上の位置順に並べるだけになる。この場合、次の2つの問題が残る。
  * **ページのヘッダー・フッター**: 文書名・章名・ページ番号・社名・機密区分などが全ページに繰り返し出て、本文の途中に何度も挟まる。Word では、同じ理由でヘッダー・フッターを既定で出力しない (REQ-F-017: 反復ノイズが RAG の検索品質を下げるため)。PDF でも同じ問題が起きる。
  * **段組み**: 2段組みなどの PDF でテキストを上から下へ、左から右へ機械的に並べると、左右の段の行が交互に混ざる。そうなると文が途中で切れ、意味の通らないチャンクができて、埋め込みと検索の品質が大きく落ちる。
* タグ付き PDF では、ヘッダー・フッターが `Artifact` として論理構造の外に置かれ、読み順も論理構造ツリーの順序で決まることが多い。そのため上の問題は主に**論理構造の無い (タグなし) PDF** で起きる。ただし、タグ付き PDF でもヘッダー・フッターが `Artifact` として正しくマークされていない文書はありうる。

## 変更要求の内容

* **ヘッダー・フッターの除去**
  * ページの上端・下端の領域で、複数のページに繰り返し現れるテキストを、ページのヘッダー・フッターと判定する。判定したテキストは既定で出力しない。数字だけが変わるページ番号 (`1`、`- 2 -`、`3 / 10` など) も繰り返しとみなす。
  * タグ付き PDF では、`Artifact` (特に `/Type /Pagination` の `/Subtype /Header`・`/Footer`) としてマークされた内容を出力しない。マークの無い繰り返しテキストにも、タグなし PDF と同じ判定を当てるかどうかは P003 で決める。
  * 除去を無効にして、ヘッダー・フッターも本文として出力するオプションを用意する。Word のヘッダー・フッターのオプション (REQ-F-017) と対応させる。オプション名や、Word 側のオプションとまとめるかどうかは P002 で決める。
  * 1ページしか無い文書など、繰り返しを判定できない場合は除去しない。本文を誤って消すほうが、ノイズが残るより RAG にとって有害だからである。
* **段組みの読み順の補正**
  * タグなし PDF で、ページ上のテキストの配置 (座標) から段組み (2段・3段など) を検出し、段ごとに上から下へ読み、左の段から右の段へ進む順に並べ替える。
  * 段の幅をまたぐ要素 (表題・全幅の図表・段抜きの見出しなど) は、ページ上の縦の位置に応じて、段の前後の正しい位置に置く。
  * タグ付き PDF では、論理構造ツリーの順序を読み順の正とし、座標による並べ替えは行わない。論理構造の順序をタグ付けした人の意図として尊重するためである。
  * 縦書きの段組みは、本CRの要求に含めない。依頼者が不要と明言した (2026-10-14)。
* **補正の結果の記録**: ヘッダー・フッターを除去したことと段組みを検出したことは、front matter の `stats` または `warnings` で分かるようにする。項目名と配置は P003 で決める。

## 期待する振る舞い

* 全ページの上端に同じ文書名が、下端にページ番号があるタグなし PDF (3ページ以上) を変換すると、文書名とページ番号が本文中に現れない。
* ページ番号の数字だけが変わるフッター (`- 1 -`、`- 2 -`、…) が、繰り返しとして除去される。
* ヘッダー・フッターの位置にあっても、1ページにしか現れないテキスト (表紙のタイトルなど) は除去されない。
* 1ページだけの PDF を変換すると、ページ上端・下端のテキストも除去されずに出力される。
* ヘッダー・フッターの除去を無効にするオプションを指定すると、ヘッダー・フッターのテキストが本文として出力される。
* `Artifact` として Header/Footer がマークされたタグ付き PDF を変換すると、それらのテキストが出力されない。
* 2段組みのタグなし PDF を変換すると、左の段のテキストがすべて出力された後に右の段のテキストが出力され、左右の段の行が混ざらない。
* 段の上に全幅の表題があり、その下が2段組みになっているページを変換すると、表題 → 左の段 → 右の段の順に出力される。
* 1段組み (段組み無し) のタグなし PDF の出力順は、段組みの補正を入れる前と変わらない (上から下)。
* タグ付き PDF を変換すると、論理構造ツリーの順序で出力され、座標による並べ替えはされない。
* 出力の front matter から、ヘッダー・フッターを除去したことと段組みを検出したことが判別できる。
* 同じ PDF を同じオプションで2回変換すると、`converted_at` を除いて同一の Markdown が出力される (REQ-NF-018)。ヘッダー・フッターの判定と段組みの検出に、非決定的な要素を含めない。

## 影響が想定される範囲

P901時点での見積もりであり、確定した対応範囲ではない (確定は P903 が `docs/P903-cr-records/CR-002.md` に記録する)。

* 前提: CR-001 (PDF 入力の追加) の PDF パーサと中間表現への写像の上に構築する。CR-001 より先には対応できない。
* 要件 (P001): CR-001 で新設する PDF 変換の節に、ヘッダー・フッター除去と読み順補正の要求IDを追加する。§4.7 の CLI オプションの表 (除去を無効にするオプション) と、§7.1 の front matter にも影響する。
* 画面 (P002 = CLI): ヘッダー・フッターのオプションの追加 (既存の Word のヘッダー・フッターのオプションと統合するかの判断を含む)。
* API (P003): PDF パーサ内のレイアウト解析の処理 (テキストブロックの座標の取得、ページ間の繰り返しの判定、段の検出)。使える情報はライブラリ選定 (CR-001 で決める) に左右される。例えば pdfminer.six・pdfplumber は文字単位の座標とレイアウト解析 (`LAParams`) を持つ。
* データモデル: 中間表現自体の変更は不要の見込み。パーサ側で並べ替えと除去を済ませてから中間表現に写す。
* 性能: ページ間の繰り返しの判定は、文書全体を見てから決める必要がある (2パス、またはページごとの情報を保持)。大きな PDF でのメモリ使用量に注意する (REQ-NF-001 系)。
* テスト: 2段組み・全幅の表題付き段組み・ヘッダー/フッター付き・1ページだけ・`Artifact` マーク付きタグ付き PDF のフィクスチャが必要になる。
* 関連ADR:
  * 既存ADRに抵触する要望は無い。
  * ヘッダー・フッターを既定で除去する方針は、Word の REQ-F-017 と同じ考え方である。
  * ヘッダー・フッターの判定方式 (繰り返しの検出の閾値・領域) と、段組みの検出方式は、新たな技術的決定として ADR の追記対象になりうる (判定は P021/P905)。

## 優先度の判断理由

* 影響度: 高。タグなし PDF は流通している PDF の多くを占めると見込まれ、そのすべての変換品質 (チャンクの意味の一貫性) に関わる。
* 緊急度: 低。CR-001 が未対応で、PDF 変換自体がまだ存在しないため、今すぐ困っている状態ではない。
* ルーブリック (影響度: 高 × 緊急度: 低) を当てはめて、優先度は **中** とする。CR-001 と同じ Refactor サイクルで続けて対応する。優先度とこの対応順は依頼者が承認済み (2026-10-14)。

## 備考

* CR-001 と分けた理由: CR-001 は「PDF を読み、論理構造があれば構造を、無ければテキストを出す」という基本的な変換を扱う。本CRは、ページ上の座標を使ったレイアウト解析という、独立した仕組みを追加する。この2つは受け入れ条件も、テストフィクスチャも、技術的な判断 (判定の閾値など) も異なる。分けておけば、P904 で反映を確かめるときと、後で品質の問題を追うときに、範囲を絞りやすい。
* フォントサイズなどによる見出しの推定は行わない。依頼者が不要と明言した (2026-10-14)。
