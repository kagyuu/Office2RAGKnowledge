# CR-001 — PDF を入力形式に追加し、論理構造があれば章立て・箇条書きに変換する

## 起票日

2026-10-14

## 起票者

* HONDOH Atsushi (本アプリのオーナー)。Claude Code セッションでの口頭依頼 (2026-10-14)
* 依頼原文: 「PDF を読み込んで Markdown にする機能も追加してほしいです。PDF に論理構造（「アクセシビリティ対応」）があれば、それをもとにMarkdown の章立て (# ## ###) や箇条書き (* ** ***) に変換してください。論理構造が無ければ単純なテキストの羅列として Markdown にしてください。PDF 中の図表からテキストを抽出できれば Word Excel PowerPoint と同様に扱って Markdown に抽出してください。」

## 背景・課題

* 現行の対応入力形式は OOXML (Word / Excel / PowerPoint) のみである (`docs/P001-requirement.md` §3.1)。社内・社外の文書は PDF で流通・保管されていることも多いが、PDF は「その他」の扱いでスキップされ、警告が出るだけになっている。そのため RAG のナレッジに取り込めない。
* 利用者は、PDF を別のツールで Markdown にするか、元の Office ファイルを探し出す必要がある。別ツールを使うと、本アプリの出力形式 (front matter・見出し構造・図形テキストブロック) と揃わず、RAG パイプライン側でチャンク分割の規則を分けなければならない。
* アクセシビリティ対応の PDF (タグ付き PDF。論理構造ツリー `StructTreeRoot` を持つもの) には、見出し (`H1`〜`H6`/`H`)・リスト (`L`/`LI`)・表 (`Table`/`TR`/`TD`)・図 (`Figure`) などの論理構造が格納されている。これを使えば、Word と同じように構造を保った Markdown を作れる。

## 変更要求の内容

* **入力形式の追加**: `.pdf` を対応入力形式に加える (`docs/P001-requirement.md` §3.1 の入力表、§3.2 の出力表、REQ-F-001 の形式判定)。出力は Word・PowerPoint と同じく `{ステム}.md` の1ファイルとする。
* **論理構造がある PDF (タグ付き PDF)**: 論理構造ツリーを辿って次のように変換する。
  * 見出しタグ (`H1`〜`H6`) を Markdown の見出し (`#`〜`######`) にする。Word の REQ-F-011 に相当する。
  * リストタグ (`L`/`LI`/`Lbl`/`LBody`) を、ネストの深さを保った Markdown リストにする。Word の REQ-F-012 に相当する。
    * 依頼原文の「箇条書き (* ** ***)」は、ネストの深さを示したものと解釈する。リテラルの `**` は CommonMark では強調記法と衝突するため、出力は既存レンダラと同じく `-` とインデントでネストを表す (例: `- 項目` / `  - 子項目` / `    - 孫項目`)。REQ-F-010 (CommonMark + GFM) に合わせるためである。この解釈は依頼者が承認済み (2026-10-14)。
  * 表タグ (`Table`) を GFM テーブルにする。Word の REQ-F-013 に相当する。
  * 段落タグ (`P` など) を段落にする。
* **論理構造が無い PDF (タグなし PDF)**: ページ順にテキストを抽出し、見出しの推定をせず、単純なテキストの羅列 (段落の並び) として Markdown に出力する。
  * フォントサイズなどから見出しを推定する処理は、本CRの要求に含めない。依頼原文が「単純なテキストの羅列」と明示しているため。
* **図表内のテキスト**: PDF の図表 (ベクター描画の図・表) に含まれるテキストを、テキストとして取り出せる場合は抽出する。抽出結果は、Word・Excel・PowerPoint の図形テキスト (`docs/P001-requirement.md` §4.4) と同じ扱いで Markdown に出力する。
  * タグ付き PDF の `Figure` 要素に代替テキスト (`/Alt`) がある場合は、画像の代替テキスト (REQ-F-048) と同じく扱う。
  * 図表がラスター画像として埋め込まれ、文字を含まない場合は抽出しない。OCR を行わない方針 (§1.4・REQ-F-070・ADR に準ずる) を PDF でも維持する。
* **front matter**: `source_format` に `pdf` を追加する (§7.1)。`title`・`author`・`created_at`・`modified_at` は PDF の文書情報辞書または XMP メタデータから取る。論理構造の有無 (タグ付きかどうか) を、front matter (例: `stats` や新規項目) で判別できるようにする。項目名・配置は P003 で確定する (依頼者承認済み、2026-10-14)。
* **CLI / ライブラリ API**: `convert`・`inspect` サブコマンドとライブラリ API で、PDF を他形式と同じように扱えるようにする (§4.7・§4.8・§9)。`inspect` では、ページ数と論理構造の有無を表示する。
* **エラー処理**: パスワードで保護 (暗号化) された PDF や破損した PDF に対しては、既存形式と同じく原因と対処が分かるメッセージを出し、バッチを止めない (REQ-F-006・REQ-F-093・REQ-NF-005)。

## 期待する振る舞い

* `.pdf` ファイルを `convert` に渡すと、`{ステム}.md` が1ファイル出力され、変換は成功として数えられる (現行のように「その他」としてスキップされない)。
* ディレクトリを入力として渡したとき、配下の `.pdf` が他の対応形式と同じく変換対象として列挙される。
* 見出しタグ `H1`/`H2`/`H3` を持つタグ付き PDF を変換すると、それぞれが `#`/`##`/`###` の見出しとして、文書の順序どおりに出力される。
* 2段以上にネストしたリスト (`L` > `LI` > `L` > `LI`) を持つタグ付き PDF を変換すると、ネストの深さに応じてインデントされた Markdown リストが出力される。
* `Table` タグを持つタグ付き PDF を変換すると、その表が GFM テーブルとして出力される。
* 論理構造を持たない PDF を変換すると、見出し記号やリスト記号を付けずに、ページ順のテキストが段落の並びとして出力される。
* 論理構造を持たない PDF の変換でエラーにならず、変換は成功として数えられる。
* テキストとして描画された文字を含む図 (ベクター図) を持つ PDF を変換すると、図中の文字列が Markdown に現れる。出力の形式は、既存形式の図形テキストブロックと同じである。
* タグ付き PDF の `Figure` に代替テキストがある場合、その代替テキストが Markdown の画像記法の alt として出力される。
* 文字を含まないラスター画像だけのページ (スキャン PDF) を変換しても、OCR は行われない。テキストが得られなかったことが警告として front matter の `warnings` に記録される。
* 出力 Markdown の front matter の `source_format` が `pdf` である。
* 出力 Markdown の front matter から、入力 PDF が論理構造を持っていたかどうかを判別できる。
* パスワードで保護された PDF を変換すると、パスワード保護を原因とするエラーメッセージが出て、そのファイルだけが失敗として数えられ、後続ファイルの処理は続く。
* 破損した PDF を変換すると、スタックトレースを出さずに、破損を原因とするエラーメッセージが出る (`--verbose` 時を除く)。
* `inspect` に PDF を渡すと、ページ数と論理構造の有無が表示される。
* 同じ PDF を同じオプションで2回変換すると、`converted_at` を除いて同一の Markdown が出力される (REQ-NF-018)。
* PDF の変換中に外部ネットワーク通信を行わず、追加の外部バイナリも要求しない (REQ-NF-010・REQ-NF-019)。

## 影響が想定される範囲

P901時点での見積もりであり、確定した対応範囲ではない (確定は P903 が `docs/P903-cr-records/CR-001.md` に記録する)。

* 要件 (P001): §1.1 (アプリの目的の文言「Office 文書」)、§3.1・§3.2 (入出力形式)、§4 (PDF 変換の節と要求IDの新設)、§4.7 (`inspect` の表示項目)、§7.1・§7.2 (front matter と構造の骨子)、§8.3 (PDF 読み取りライブラリの選定)、§11 (用語)。
* 画面 (P002 = CLI): `inspect` の出力項目 (ページ数・論理構造の有無)、エラーメッセージ (暗号化・破損した PDF)、対応拡張子のヘルプ文言。
* API (P003 = ライブラリ公開API): `detect_format` の戻り値に `pdf` を追加、`parsers/pdf.py` (新規) の追加。
* データモデル: 中間表現 `Document` は既存の見出し・リスト・表・段落・図形テキストのブロックで表せる見込み。ページ境界の扱いは決める必要がある (REQ-F-020 では改ページを保持しない)。front matter の `source_format` の値域と、論理構造の有無を表す項目を追加する。
* アーキテクチャ: 現在は「パーサ → `ooxml/` → 中間表現 → レンダラ」の構成で、形式判定・ZIP 爆弾検査・パストラバーサル検査が OOXML (ZIP) を前提にしている (`docs/ArchitectureHandbook.md` §2・§6)。PDF は ZIP ではないため、形式判定 (マジックバイト `%PDF-`) と安全性検査 (巨大ストリーム・展開爆弾への上限) を PDF 向けに用意する必要がある。`ShapeTextExtractor` は OOXML 専用なので、PDF の図表テキストは PDF パーサ側で中間表現の図形テキストに写すことになる見込み。
* 依存ライブラリ: PDF の論理構造ツリーとテキストを読むライブラリが新たに必要になる。候補の例は pypdf・pdfminer.six・pdfplumber・pikepdf・PyMuPDF。選定は P003 が行う。
  * PyMuPDF は AGPL-3.0 であり、本アプリのライセンス (MIT) と配布方針に影響するため、選定時に考慮が必要である。
  * 外部バイナリを要しないこと (REQ-NF-019) とオフライン動作 (REQ-NF-010) を満たす必要がある。
* セキュリティ: PDF に埋め込まれた JavaScript・外部参照・埋め込みファイルを実行も解決もしないこと (REQ-NF-009・REQ-NF-010 の PDF 版)。巨大な圧縮ストリームへの上限 (REQ-NF-006 の PDF 版)。
* テスト: PDF のテストフィクスチャ (タグ付き / タグなし / 図表テキストあり / 暗号化 / 破損 / スキャン画像のみ) が新たに必要になる。フィクスチャ生成の手段も決める必要がある。
* 関連ADR:
  * ADR-008 (ステートレス)・ADR-010 (エスケープ方針)・ADR-011 (CLI とライブラリの UI 分離) は PDF にもそのまま適用される見込み。
  * OCR を行わない方針 (P001 §1.4 ★ACCEPTED★) は維持する。本CRは「テキストとして取り出せる場合に限り」図表テキストを抽出する要求なので、この方針には抵触しない。
  * 既存ADRを覆す要望は含まない。ただし PDF 読み取りライブラリの選定と、タグ付き / タグなしの分岐方針は新たな技術的決定になる見込みで、ADR の追記対象になりうる (判定は P021/P905)。

## 優先度の判断理由

* 影響度: 高。入力形式そのものの追加で、PDF で文書を持つすべての利用者と、主要機能 (`convert`・`inspect`) に関わる。
* 緊急度: 低。既存の Office 変換機能は影響を受けずに動いている。PDF については、別ツールでの変換や元の Office ファイルの利用という回避策がある (手間は大きい)。
* ルーブリック (影響度: 高 × 緊急度: 低) を当てはめて、優先度は **中** とする。依頼者が承認済み (2026-10-14)。

## 備考

* 本アプリの名称 (Office2RAGKnowledge) と、要件定義上の位置づけ (Office 文書の変換ツール) は、PDF の追加後も変えない前提で起票した。この前提は依頼者が承認済み (2026-10-14)。
* フォントサイズなどによる見出しの推定 (タグなし PDF の構造の推定) は行わない。依頼者が不要と明言した (2026-10-14)。
* ページのヘッダー・フッターの除去と、段組みの読み順の補正は、依頼者の追加要望 (2026-10-14) により [CR-002](./CR-002.md) として別途起票した。本CRは PDF の基本的な読み取りと変換までを対象とし、CR-002 は本CRの PDF パーサを前提とする。
