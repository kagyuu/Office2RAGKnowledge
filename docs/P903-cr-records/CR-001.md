### 事前のスコープ想定と実際の差異

* **ライブラリの変更**: 着手時のスパイクでは MIT の pdfminer.six を採る設計としていたが、P003 作成中に依頼者から「いったん PyMuPDF で最後まで実装し、その後 Docling・PDF Inspector での代替を検討する」との指示があり、PyMuPDF に切り替えた。差し替えに備えて依存を `pdf/backend.py` に閉じ込めた (ADR-012)。
* **実装中に判明した MuPDF の挙動への対処** (設計の意図は変えずに P003 に追記): 構造の後の Artifact が直前の要素に含まれる問題 (`pdf/content.py` を追加)、画像だけの図が構造化テキストに現れない問題、経路の数え方の突き合わせ、段の幅の条件 (P003 §7A.2・§7A.9、Handbook §4-13・§4-14)。
* **P302 での追加の是正**: 開発時依存 `pypdf` → `pypdf[crypto]` (新規 venv で初めて検出。Handbook §9-16)。
* **想定外に解消できたこと**: Docker のビルド・実行と Python 3.11 での全件実行 (前回の P302 の要対応2件) を、改修環境 (WSL2) で確認できた。

### 反映確認の結論

* **17項目すべてを確認できた。不足は無い。**
* スコープ決定 (P002〜P302 をすべて再オープン) は妥当だった。CLI・公開 API・中間表現・パーサ・レンダラ・テスト・配布のすべてに変更が入っており、対象外にできたフェーズは無かった。
* 依頼者の追加指示 (PyMuPDF で実装し、後で代替を検討) を反映した結果、**配布物のライセンス (AGPL-3.0 の依存) という CR-001 の期待する振る舞いには含まれない課題**が残っている。これは反映の不足ではなく、`docs/P302-deliver.md` 10.1章① と ADR-012 で管理する出荷判断の事項である。
* 既知の挙動として、MCR 辞書形式でタグ付けされた PDF はタグなしとして変換される (警告付き。Handbook §4-8)。期待する振る舞い #3〜#5 は、整数 MCID 形式 (Word 等が出力する一般的な形式) で確認した。

## ADR更新確認(P905が記載)

* ADR更新: **要** (理由: CR-001 は新たな技術的決定を2つ含む。① PDF 読み取りライブラリの選定とその依存の閉じ込め、② タグ付き/タグなしの判定方式と、タグなしで構造を推定しない方針。いずれも後続の改修で理由を問われやすい)
* 更新した場合の該当ADR番号: **ADR-012** (PyMuPDF の採用と `pdf/backend.py` への閉じ込め。状態は「採用 (暫定。ライセンスの検討待ち)」)、**ADR-013** (被覆率 50% による判定、タグなしは構造を推定しない)

* 既存の ADR-001〜011 を覆す決定は無い。ADR-008 (ステートレス)・ADR-010 (エスケープ)・ADR-011 (UI) は PDF にもそのまま適用されることを確認した。
* **申し送り**: ADR-012 は、依頼者の指示による代替ライブラリの検討 (Docling・PDF Inspector・pdfminer.six) の結論が出た時点で、状態を「採用」に確定するか、別の ADR で置き換える (廃止する場合は `docs/ADR_master.md` へ退避する)。
