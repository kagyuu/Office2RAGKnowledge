## 1. テストレベルの定義と目的

V字モデルに沿って4レベルに分ける。本アプリは CLI アプリケーションであり、Web システムを前提とした一般的な定義を次のとおり読み替える。

| テストレベル | 目的 | 本アプリでの対象 | 定義するフェーズ | 実行するフェーズ |
| --- | --- | --- | --- | --- |
| **単体テスト** | P002・P003 で定義した画面 (CLI) と API が、単体で仕様どおり動くか | 個々の関数・クラス (パーサ / レンダラ / 検証 / エスケープ / 型) | P007 (スプリント内) | P102 |
| **結合テスト** | 画面と API が連携して仕様どおりか | パーサ→中間表現→レンダラの連鎖、CLI→API→ファイル出力の連鎖 | P008 | P103 |
| **システムテスト** | P001 の要件・非機能要件を満たしているか | 性能・メモリ・セキュリティ・冪等性・並列 | P009 | P201 |
| **受け入れテスト** | 利用者・運用者の視点で、本番相当環境で問題なく使えるか | 実際の利用シナリオ (バッチ変換・パイプ・エラー対処・再実行) | P009 | P201 |

**単体テストとスプリント内結合テストは `docs/P007-impl-direction.md` / `docs/P008-test-direction.md` で、スプリント横断・システム・受け入れテストは `docs/P009-acceptance-direction.md` で、本計画をもとに実装指示を別途作成する。**

### 2.3 運用観点 (再起動耐性)

**本アプリは永続化データストアを持たないため、マイグレーションの冪等性に起因する「2回目以降の起動が失敗する」問題は生じない** (P003 §3.1)。したがってマイグレーション観点の再起動テストは対象外である。

ただし、**本アプリには別の理由で「2回目の実行」に関する確認が必要**であり、これを独立した観点として明示する。単体テスト・結合テストはテストごとに一時ディレクトリを作るため常に「初回実行」となり、**この観点を検出できない**。

| # | 観点 | 担当レベル | 内容 |
| --- | --- | --- | --- |
| **O-01** | **同一出力先への2回目の実行** | **受け入れテスト (P009)** | 同じ出力先に対して2回続けて `convert` を実行し、`--on-exists skip` で既存分がスキップされ、`overwrite` で上書きされること。**終了コードとサマリの件数が期待どおりであること** |
| **O-02** | **Excel の二重出力で片方だけが既存の場合** | **受け入れテスト (P009)** | `{ステム}.table.md` のみを残して再実行し、table 側はスキップ、grid 側は書き出されること (P002 §5.2)。**出力ファイルごとに個別判定されることの確認** |
| **O-03** | **テストスイートの2回連続実行** | 全レベル (P103・P201 が確認) | テストスイート全体を2回続けて実行し、同じ結果になること。前回実行の出力ファイルが残ることで2回目が失敗しないこと |

O-01・O-02 は永続化された出力ディレクトリに対して実行する必要があり、一時ディレクトリを用いる単体テスト・スプリント内結合テスト (P007/P008) では代替できないため、**受け入れ結合テスト (P009) が担当する**。

## 3. テストデータの準備方針

### 3.1 生成する / 固定する の判断

| 種別 | 方針 | 理由 |
| --- | --- | --- |
| **コードで生成する** | 通常の Word 文書、Excel の表・方眼紙シート・複数表領域・キャッシュ値なし数式、PowerPoint のスライド・表・ノート | python-docx / openpyxl / python-pptx で生成でき、バイナリをリポジトリに置かずに済む。**キャッシュ値なしの数式は openpyxl で書き出せば自動的にその状態になる** (P003 §1.2 で実証) |
| **XML 文字列を直接与える** | 図形テキストの抽出 (`mc:AlternateContent`、グループ、SmartArt、グラフ) | 抽出器は XML 要素を入力とする純粋な関数であり、ファイルを作らずにテストできる。**P003 §1.3 のスパイクで用いた再現 XML をそのまま単体テストに固定する** |
| **固定フィクスチャを置く** | 実際のグループ図形を含む `.pptx` / `.docx`、SmartArt を含むファイル、キャッシュ値を**持つ**数式を含む `.xlsx` | 生成ライブラリがこれらを作る API を持たない (python-pptx はグループ生成 API を持たない、openpyxl は数式を計算しない) |
| **プログラムで細工する** | ZIP 爆弾、パストラバーサルを含む ZIP、XXE を含む XML、破損ファイル | 正常なファイルを生成してから ZIP を書き換える。**リポジトリに悪意あるファイルを置かない** |

### 3.2 固定フィクスチャの扱い

| 項目 | 方針 |
| --- | --- |
| 配置 | `tests/fixtures/` |
| 内容 | **機微情報を一切含めない**。すべて本プロジェクトのために作成した無害な内容とする |
| サイズ | 1ファイル 100KB 以下を目安とする。大きなファイルはリポジトリを重くするため |
| 生成手順の記録 | フィクスチャごとに `tests/fixtures/README.md` に「何を含むファイルか」「どう作ったか」を記載する。後から再作成できるようにするため |

★FIXME★ グループ図形・SmartArt を含む固定フィクスチャは、Office アプリケーションが無い環境では作成できない。**P102 の実装時に、OOXML を直接組み立てて生成するスクリプト (`tests/fixtures/build_fixtures.py`) を用意する方針とする。** この方式で実 Office が生成するファイルと同等の構造になるかは、実装時に確認を要する。困難な場合は、当該テストを「XML 文字列を直接与える」方式に切り替え、その旨を記録する。

### 3.3 大きなファイルの扱い

性能テスト (N-01〜N-03) 用の大きなファイル (50MB 級) は**リポジトリに含めず、テスト実行時に生成する**。生成に時間がかかるため、性能テストは既定で `pytest -m perf` のマーカー付きとし、通常のテスト実行から除外する。

## 4. テストデータのライフサイクル方針

**本アプリは永続化データストアを持たないため、DB のベースライン復元という概念は存在しない。** 代わりに、テストが生成する**出力ファイル**が同じ問題 (2回目の実行だけ失敗する) を引き起こしうるため、これを対象として方針を定める。

### 4.1 ベースラインへ復元する単位

| テストレベル | 復元単位 | 実現方法 |
| --- | --- | --- |
| 単体テスト | **テスト1件ごと** | pytest の `tmp_path` フィクスチャを使う。テストごとに新しい一時ディレクトリが与えられ、テスト間でファイルを共有しない |
| 結合テスト | **テスト1件ごと** | 同上 |
| **受け入れテスト (O-01・O-02)** | **テストスイートの実行ごと** | 2回目の実行の挙動を検証することが目的であるため、テスト内で意図的に同じディレクトリを2回使う。ディレクトリはスイート開始時に作り直す (`tmp_path_factory`) |

**既定は「テストスイートの実行ごと」ではなく「テスト1件ごと」とする。** `SKILL-P006` は既定をスイート単位としているが、これは共有データストアを持つアプリを想定した既定である。本アプリのテストは**出力先ディレクトリ以外に共有状態を持たない**ため、テストごとの隔離が安全かつ単純であり、テスト間の依存も生じない。
★ACCEPTED★ 検討: スイート単位の復元を既定とする案 (SKILL の既定に合わせる) を検討したが、本アプリでは各テストが独立した一時ディレクトリを持てるため、テスト間でファイルを共有する理由がない。スイート単位にすると、あるテストが書いた出力が別のテストの `--on-exists skip` に影響し、実行順に依存する不安定なテストになる。残存リスク: SKILL の既定と異なるため、他プロジェクトの慣習と食い違う。本節の記載で意図を明示することで対処する。

### 4.2 「ベースライン」が指すもの

本アプリにおけるベースラインは **「出力先ディレクトリが存在しない、または空である状態」** を指す。

* マイグレーションや初期データ投入に相当するものは存在しない。
* 入力ファイル (フィクスチャ・生成ファイル) は読み取り専用であり、テストが変更しない。したがって復元の対象外である。
* 設定ファイル (`office2rag.toml`) を用いるテストは、一時ディレクトリ内に生成し、カレントディレクトリを切り替えて実行する。**リポジトリ直下に `office2rag.toml` を置かない** (置くと全テストが暗黙にそれを読み、テストの独立性が壊れる)。

### 4.3 テスト間のデータ依存

**テスト間のデータ依存を許容しない。** 各テストは自身の入力を用意し、自身の一時ディレクトリに出力する。例外は受け入れテスト O-01・O-02 のみであり、これらは**1つのテスト関数の中で**2回実行を行う (テストをまたいだ依存ではない)。

### 4.4 再実行可能性の確認

**テストスイートを2回続けて実行し、同じ結果になることを確認する** (観点 O-03)。確認するのはスイート全体の再実行であり、個々のテストの単独実行可能性ではない。

* この確認は、テストを新規作成・変更したフェーズ (P103・P201・P203・P205) が行う。
* 2回目が失敗する場合は**テスト側の欠陥**として扱い、本節の方針に立ち返って是正する (アプリケーションコードの欠陥として扱わない)。

## 5. モック・スタブの方針

| 対象 | 方針 | 理由 |
| --- | --- | --- |
| **外部 API** | **モックしない (そもそも存在しない)** | 本アプリは外部通信を一切行わない (REQ-NF-010)。モックすべき外部依存がない |
| ファイルシステム | **モックしない**。`tmp_path` で実ファイルを使う | 実際のファイル入出力・権限・パス長が検証対象に含まれるため、モックすると検証の意味が失われる |
| openpyxl / python-docx / python-pptx | **モックしない** | これらの挙動そのもの (キャッシュ値の扱いなど) が仕様の前提であり、モックすると前提の誤りを検出できない |
| 並列実行 (`ProcessPoolExecutor`) | **モックしない**。`--jobs 2` で実際に並列起動する | Windows の `spawn` に起因する不具合 (P005 R5) は、モックでは検出できない |
| 時刻 (`converted_at`) | **固定しない**。比較時に除外する | P003 §11 の方針。`--no-front-matter` を用いた比較、または front matter を除去してから比較する |
| 権限エラー (E-003/E-004) | OS 依存のため、**書き込み不可ディレクトリを実際に作る**。作成できない環境ではスキップする | Windows と POSIX で権限モデルが異なる。`pytest.mark.skipif` で環境依存を明示する |

**「モックしない」を基本方針とする理由**: 本アプリの価値の中心は「実際の Office ファイルを正しく読めること」にあり、テストでライブラリや I/O をモックすると、まさに検証したい部分が検証されなくなる。テストの実行速度より、検証の実効性を優先する。

## 7. 重点テスト領域

本アプリの中核要求について、テストを厚く置く領域を明示する。

### 7.1 オートシェープ内テキスト (F-09) — 利用者の最重要要求

P001 §10 が「専用のテスト群を設ける」と定めた領域。**形式ごとに次を網羅する。**

| # | ケース | 単体 | 結合 |
| --- | --- | --- | --- |
| 1 | 単独の図形 (テキストあり) | ● | ● |
| 2 | テキストを持たない図形 (ブロックを作らない: INV-05) | ● | |
| 3 | **グループ図形 (2階層以上)** — 再帰の確認 | ● | ● |
| 4 | **`mc:Choice` / `mc:Fallback` の二重構造** — 二重出力しないこと | **●** | |
| 5 | SmartArt (階層あり) | ● | ● |
| 6 | テキストボックス | ● | ● |
| 7 | 図形内の表 (引用の外に出す) | ● | ● |
| 8 | 図形内の複数段落 (区切りの保持) | ● | |
| 9 | グラフ (タイトル・系列名・カテゴリ名) | ● | |
| 10 | Excel: アンカーセル参照の併記・章末への配置 | ● | ● |
| 11 | Word: アンカー段落の直後・位置不明の末尾集約 | ● | ● |
| 12 | PowerPoint: プレースホルダと二重にしない | ● | ● |

**ケース4は必ず単体テストに置く。** P003 §1.3 で実測した落とし穴であり、テストがなければ再発する。

### 7.2 Excel の二重出力と表領域 (F-04〜F-08) — 要求①②③

| # | ケース | レベル |

## 8. カバレッジ目標

★ACCEPTED★ 検討: `--cov-fail-under=80` で機械的に落とす案を検討したが、CLI の表示部やエラーハンドリングの一部は自動テストでの到達コストが高く、閾値を満たすためだけの薄いテストを書く動機が生じる。**カバレッジは目標であって合格条件ではない**とし、代わりに §7 の重点領域を網羅することを合格条件とする。残存リスク: カバレッジが徐々に低下しても機械的に検出されない。P103 の記録で推移を追う。

## 9. 性能テストの方針

| 項目 | 方針 |
| --- | --- |
| 実行 | `pytest -m perf` で明示的に実行する。通常のテスト実行から除外する |
| 計測 | 所要時間は `time.perf_counter`、メモリは `tracemalloc` のピーク値と OS のプロセス常駐メモリ (取得できる場合) |
| 判定 | **閾値による自動判定を行わず、実測値を記録する** (P001 §10 の方針) |
| 記録先 | `docs/test-records/YYYYMMDD-HHMM-test-record.md` |
| 対象 | N-01 (1ファイル10秒)、N-02 (バッチ劣化1.5倍)、N-03 (50MBで2GB)、および **Excel 二重出力が単一モードの2倍を要しないこと** (REQ-F-068) |
